# Git Workflow

> Binding conventions for committing and reviewing changes in this repo.

## Tooling

- Use the **`git-commit`** skill when the user asks to commit. It stages
  intelligently and generates conventional commit messages from the diff.
- Commit only when explicitly asked. Never commit secrets.

## Branching

- Work on a feature branch; keep `main` releasable. The repo tracks `main`
  (default branch).
- Name branches by intent: `feature/<area>`, `fix/<area>`, `refactor/<area>`,
  `chore/<area>`.

## Commit message style

Follow Conventional Commits, matching the repo's existing history:

```
<type>(<scope>): <imperative summary>

- optional bullet points for notable details
```

- Types: `feat`, `fix`, `refactor`, `perf`, `docs`, `chore`, `test`, `style`.
- Scope examples: `pos`, `products`, `customers`, `auth`, `i18n`, `reports`,
  `budgets`, `api`, `agents`.
- Summary in the imperative mood, ≤ 72 chars. Body bullets explain "why", not
  "what".

## What never goes into a commit

- `.env`, `.env.local` (contain `NEXT_PUBLIC_API_URL`; already gitignored — keep it that way).
- `.next/`, `node_modules/`, `tsconfig.tsbuildinfo`.
- `dev.log`, `dev-err.log`, `repomix-output.xml` (working artifacts).
- Secrets, tokens, or API keys — the access token is never persisted anyway.

## Reviewing your own work

- Before committing, run `git status` and `git diff`, then stage only intended files.
- Run `npm run lint` and `npm run build` before committing changes.
- Use the `code-review` skill for a two-axis review (standards vs spec) when the
  user asks to review a branch/PR/diff.
- If a commit fails or a hook rejects it, fix and make a new commit — don't amend
  the failed one.

## Keeping `.agents/` in sync

- New/changed docs under `.agents/` should be committed alongside the code they
  describe so agents always see current conventions.
- The `skills-lock.json` and `.agents/skills/` are generated by the skills CLI —
  commit them so skill versions are reproducible.
